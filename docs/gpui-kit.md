# GPUI Kit 开发规则(v2,完整版)

建议放置位置:`.claude/rules/gpui-kit.md`,仅对 `esdeck-app` 下的 Rust 文件生效,并在 `CLAUDE.md` 中引用。

来源:GPUI Kit 官方 Coding Guides 与 Design Guides(英文版与 zh-CN 版,内容一致),已通读全文:
- https://gpui-kit.com/docs/coding-guides
- https://gpui-kit.com/docs/design-guides
- https://gpui-kit.com/zh-CN/docs/design-guides/

约定:**必须**(Must)= 生命周期、正确性、生态约束;**应当**(Should)= 默认做法,偏离需要具体理由。官方明确说,具体签名以**当前源码与 API 文档**为准,本文件不包含任何 API 签名。

---

## 0. 给编码代理的前置要求(必须)
1. 修改前先读:最近的实现、它的测试、re-export 入口、相关组件文档、相邻 feature 和主题 token。
2. **必须在当前源码里搜索真实签名**。不得从 React/Shadcn/CSS 示例或旧版 GPUI 类推 API,也不得因为方法名"听起来合理"就发明方法。
3. 动手前先说清:主要任务、state owner、组件组合方式、键盘路径。
4. 每次改动要能说出:
   - 行为归属方与展示归属方
   - 保留的标识(identity)与状态生命周期
   - 指针、键盘、焦点、无障碍契约
   - 布局与溢出的归属方
   - 用到的主题 token 与有意的例外字面量
   - 一个回归时会失败的测试
5. 生成的代码必须经人审查和测试。"能编译"和"截图看着合理"都不是质量标准;键盘、焦点、动态内容、主题、缩放、失败状态都属于设计。不要做只为让生成代码好看的大范围重构。

## 1. 分层与依赖
- 依赖只向下:app shell → feature crate → app component → gpui-component → gpui-base。
- 可复用组件**不得**依赖应用界面;`gpui-base` 不得依赖 gpui-component 的主题。
- app shell 只组装窗口与 feature,几乎不含 feature 逻辑。
- 按**能力**组织,**禁止**建立全局 `models/`、`views/`、`modals/`、`commands/` 目录。
- feature 对外只暴露:刻意公开的 Entity 类型、小型 handle、领域 ID、命令、事件或接口;模型字段与实现模块保持私有。跨 feature 传递 `Entity<T>` 句柄,不要反复复制大型集合。
- feature 之间不得依赖对方的私有模块;跨 feature 调用要显式且单向,或把共享契约下沉。避免依赖环,避免万能的 `shared` crate;共享 crate 只在有明确用途和真实使用方后才抽取。
- 小能力先作为模块;有具体收益时再拆 crate。
- 只有真正全应用范围的服务才用 `Global`,并保持 feature 私有;只被一个 feature 使用的模型不是 Global。

本项目映射:`es-dsl-core`、`es-client` 不依赖 UI。`esdeck-app` 内按能力分模块(如 `connection`、`editor`、`response`、`history`),不按 view/model 分类。

## 2. 启动与 Root
- `gpui_kit::init(cx)` 只初始化一次,且在创建任何基于组件的 view 之前。
- 每个窗口第一层放一个 `Root`;不要为同一窗口内的每个页面各建一个。绕过 Root 会在覆盖层嵌套或焦点快速切换时出错。

## 3. 上下文与生命周期
- Entity 跨帧保留;`render` 返回的元素树是当前帧的新描述,二者要分清。
- **禁止**保留 `&mut Window`、`&mut App`、`&mut Context<_>` 超出被提供的那次调用;要保留就用 `Entity`、`WeakEntity`、`FocusHandle`、滚动句柄或领域 ID。
- layout、prepaint、paint 是后续阶段,仅在确实需要已解析几何时才使用其钩子。

## 4. 选择组件单元
- **默认**用 `RenderOnce` 做轻量、可复用的值型组件(标签、选中值、回调由调用方当前状态给出)。
- 只有需要持久复杂状态或独立生命周期(订阅、异步任务、历史、子 Entity、增量更新)时才用 Entity 支撑的 `Render` view。
- Entity 存在拥有它的 view 里,**不要在 `render` 中重建**。不要把每个视觉片段都做成 Entity。
- 不要强求所有组件套同一模板:语义元素、复合行为根、Entity 支撑的系统、基础设施各有各的公共接口,按行为选择。

本项目映射:编辑器、响应表格、连接树属于 Entity 系统;状态徽标、空状态用 `RenderOnce`。

## 5. 状态与所有权
- **必须**用 `SharedString` 保存跨帧或跨回调闭包保留的 UI 文本(标签、标题、占位符);不要每次渲染克隆 `String`。可变编辑缓冲用 `String`,一次调用内的临时只读访问用 `&str`。
- 会被 UI 保留的不可变 API/JSON 响应文本,在**反序列化边界**就做成 `SharedString`;保持收到的传输值不变,派生或格式化的展示文本放进单独的模型。
- 状态放在能保持其正确的最窄所有者:领域状态在模型或 feature view,临时视图状态在渲染它的 view,可复用行为状态在专用组件状态。
- 所有权链与订阅必须有界;避免状态反馈循环。
- **禁止**在 `render` 中无条件修改状态或 `cx.notify()`。
- 不要保存会与受控模型值漂移的重复本地状态;不要让一个 Entity 装下整个应用的无关状态。

## 6. 稳定标识
- 可重排的重复元素必须使用**基于领域 ID 的稳定 ElementId**,例如 `Button::new(("delete-project", project.id))`。
- **禁止**在 `render` 中生成随机 ID;**禁止**用下标做可重排数据的 ID。
- 标识变化即界面标识变化,这种重置必须是有意的。
- 转场通道、覆盖层 token、滚动句柄、持久化 ID 同理:共用同一个 key 会互相覆盖状态,每帧换 key 则永远积累不了状态。

## 7. 渲染与组合
- `render` 保持声明式:读取当前状态、推导展示值、组合元素;领域操作、解析和非平凡修改放到具名方法或服务。
- 区域有名字且能降低阅读负担时抽成 `render_<region>`;区域有自己的可复用契约或生命周期时才抽成组件,不是因为链太长。
- 统一使用组件的流式 trait(`Sizable`、`Disableable`、`Selectable` 等);小的条件调整用 `.when(...)` / `.when_some(...)`,分支代表截然不同的界面时用普通 Rust 控制流。
- **先用标准语义组件再自建**:不要用 `div` 拼菜单、Select、下拉或命令面板;不要用可点击 `div` 代替语义组件。复用才能保留条目几何、焦点转移、键盘导航、选择、禁用、关闭和无障碍契约。标准组件表达不了合理的重复模式时,改进其显式 API,而不是在每个调用点给任意后代加样式。
- 应用提供的渲染回调(列表项、菜单构造、dock 面板渲染)**必须无副作用**,因为它们可能在测量或重绘时多次运行;不得执行业务操作、追加数据或注册无界订阅。
- 不要为了重命名每个方法或冻结全部能力而包装库组件。
- 行为与展示边界:Base 负责可复用行为与实现它所需的几何,展示层负责产品视觉语言。通过 `Styled`、带类型的语义状态样式、显式部件、子槽位和条目渲染器暴露展示;**不要**检查任意后代去猜标题、描述或关闭按钮。
- 可复用行为(无产品样式)放 `gpui-base`;有主题、有主见的展示放 gpui-component 或应用。

## 8. 主题与样式(必须)
- 颜色从 `cx.theme()` 按语义角色读取,布局用 GPUI 的 `Styled` 方法。
- 应用代码**不得**出现原始十六进制、`rgb`/`rgba`、`hsla`。缺少角色就在产品主题/token 层新增。仅允许主题定义本身,或本身就是数据的已审计栅格内容。
- 应用布局使用 rem 比例的辅助方法(`p_2()`、`gap_3()`、`w_64()`、`text_sm()`),**不要**直接写 `px(...)`。每一处直接 `px(...)` 或原始颜色构造都视为评审问题;仅在有文档说明的物理/平台边界(一设备像素的发丝线、平台窗口内缩、位图尺寸、最小命中容差、必须匹配外部表面的几何)、实测运行时几何、栅格/数据颜色或 token 定义本身时才可接受。方便或为了贴合截图**不是**正当理由。
- 不要硬编码产品颜色、圆角、间距或控件几何;用语义 token 表达含义,不按调色板位置选色。
- 新的应用级展示优先用 `Theme::semantic_tokens()`;遗留的组件专属主题值仅为兼容保留,不要变成每个应用控件的扩展点。
- 与状态无关的几何放普通 builder 链;运行时交互状态用 GPUI 的 `hover`、`active`、`focus`、`focus_visible`;选中、按下、禁用外观用组件的语义状态样式。样式优先级:实例样式 → 激活的语义值状态 → 禁用状态 → GPUI 运行时交互修饰。
- 弹层归属用显式状态保存,使触发器在关闭前保持打开/按下外观;禁用控件的 hover/active 要加保护。
- 组件变体少而有意义,不要为单个调用点新增变体。
- **Primary** 只绑定决策区域真实的默认提交(通常就是 Enter 触发的动作),不由动作数量、频率或工具栏位置决定。
- Badge、Alert 变体要少且有语义;普通元数据保持中性,不要把每个枚举值映射成不同颜色。
- 修改全局主题用 `Theme::update(cx, |theme| ...)`。若用 `Theme::global_mut`,则需自行同步 tokens、调用 `Theme::sync_base(cx)` 并刷新窗口。
- 自定义间距/阴影刻度不会存进全局主题;若需要,应用自己持有 `SemanticThemeTokens` 并传给组件,不要写入全局主题后指望 `cx.theme().semantic_tokens()` 返回它。
- 带 `overflow_hidden()` 的祖先会裁掉外凸的焦点环;布局要留出空间,不能为了裁剪丢掉键盘焦点可见性。

### 缩放(rem)
- 主题基础字体 `font_size` 就是应用缩放控制,经 Root 成为窗口 rem:`Theme::update(cx, |theme| theme.font_size = px(18.))`。
- 后代 UI 用相对辅助方法(`text_sm()`、`gap_2()`、`px_3()`、`h_8()`、`size_4()`),使文字、间距、控件、图标共用一条缩放轴。自定义组件若把 rem 文字和固定像素内边距/图标混用,必须写明原因。
- 不要只放大文字:大号标签放进固定高度按钮、大号文档放进固定面板最小宽度、陈旧的虚拟列表测量都会破坏节奏。也不要把发丝线按比例放大。
- 任何依据已解析布局缓存的内容,失效键**必须包含 `window.rem_size()`**(换行行高、文本排版、虚拟列表测量、弹层/对话框几何、由文字推导的图标尺寸、自定义 canvas 度量)。
- 应用缩放不同于 Dock 面板缩放;后者不得修改窗口 rem。
- 在多个基础字号下测试:层级、换行、截断、最小窗口、面板调整、焦点环余量、弹层位置、虚拟行测量。

## 9. 事件、动作与焦点
- 指针专属行为用指针回调;需要键位绑定、菜单或多输入来源派发的命令用 GPUI **Action**,处理器放在拥有该命令的 view 附近。
- **同一个逻辑命令只建模一次**:工具栏 Button、`DropdownMenu` 项、`ContextMenu` 项、菜单栏项和键位绑定派发同一个 Action 或调用同一个所有者方法;标签、图标、快捷键、启用状态尽量由同一命令策略推导。菜单负责导航与关闭,feature 所有者负责命令是否允许及其行为。
- 命令用 `Button`(安静样式选 `outline`、`ghost` 或图标形式),**不要**换成 `Link`。`Link` 只用于由浏览器或邮件客户端打开的目标(URL、网页文档、邮箱)。应用内目的地(侧栏、标签页、面包屑、列表项、切换工作区)用对应导航组件或 Button/Action。
- 只有嵌套交互必须阻止父级处理同一事件时才停止传播。
- **先 `cx.bind_keys`,再 `cx.set_menus`**;键位表之后变化(用户键位文件、切换语言重建菜单)时再次调用 `cx.set_menus`。
- 焦点归属要显式:
  - 在拥有键盘交互的 Entity 里保留 `FocusHandle`;
  - `key_context` 与 `on_action` 放在同一个聚焦区域;
  - 打开覆盖层时转移焦点,关闭时恢复;
  - 渲染可见的 `focus_visible` 状态;
  - **不要**在 `render` 中无条件请求焦点;
  - 被追踪的句柄要成为 Tab 停靠点,需 `cx.focus_handle().tab_stop(true)`(或 `.tab_index(n)`);无状态组件可用 `window.use_keyed_state` 在 `render` 中创建该句柄。
- 复合控件要实现完整导航模型(方向键、Home/End 或翻页、确认、取消、Tab),不能只做几个孤立快捷键。
- 模态界面必须捕获焦点并在关闭时恢复到之前有效的焦点目标;嵌套覆盖层从最上层开始关闭;处理快速关/开序列,不要经由正在关闭的中间界面恢复焦点。

## 10. 异步与副作用
- 异步工作通过 `Task` 从事件、生命周期钩子或具名方法发起,**不要**作为 `render` 的无条件副作用。
- 工作不应让已关闭的 view 存活时,捕获弱 Entity;完成后通过 GPUI 上下文更新状态,处理 Entity 或窗口已不存在的情况,状态连贯变化后**只通知一次**。
- 周期性任务的句柄放在所有者上,所有者被丢弃即取消,默认不要 detach。一次性任务只有必须独立完成时才 `Task::detach()`。显式处理错误和弱 Entity 更新失败。
- 异步操作用显式状态:idle、loading、loaded、failed;刷新时尽量保留可用的旧数据;防止重复提交破坏性操作;可恢复错误要在 UI 中呈现,不能只写日志。
- 昂贵的解析/计算放后台执行器,GPUI Entity 的修改留在应用上下文。
- 结果可能在请求、文档、视图或选择变化后才到达:附带 revision 或 identity,**丢弃过期结果**。

本项目映射:补全请求、`_mapping` 加载、ES 请求执行都带 revision;用户切换连接或编辑内容后,旧结果不得写入新状态。

## 11. 布局、测量、滚动
- `h_flex` 在交叉轴**居中**,`v_flex` 默认 **stretch**。一行里放满高的列必须写 `items_stretch()`(或给列 `h_full()`、给行 `items_start()`),否则高于该行的列会被居中,顶部(常是标题)被裁出窗口。凡子元素拥有页头、页脚或需要按行高解析的滚动区域,都要这样处理。
- 大多数界面用 GPUI 布局,不要自己测量。测量只用于弹层、虚拟化、编辑器、拖拽句柄、图表等确实依赖已解析几何的组件,并放在拥有该行为的层;仅当普通布局无法表达关系时才在 prepaint 观察 bounds;**不要**每次 prepaint 修改无关应用状态;测得数据按帧/revision 作用域看待;共享几何(弹层翻转、视口夹取)集中处理。
- 对齐用"构造"而不是"修正":相邻区域共用同一个间距 token 或共享内缩;对关键重复边缘/列/间距加几何断言或视觉回归;不要只在默认窗口检查,rem 缩放和显示缩放会造成 1 物理像素漂移。
- **不要**把测得的修正写成原始 `px(...)` 微调;追溯到重复内边距、嵌套内缩、边框归属、字体度量或取整,从结构上修复。
- 主工作区用 `flex_1()`,并对允许收缩的弹性子元素加 `min_w_0()` / `min_h_0()`,否则它不会在长内容面前收缩。
- 每个可滚动区域只能有**一个所有者**;避免嵌套滚动;把 `Scrollable` 加在拥有整个面板/编辑器/窗口视口的元素上,内容内缩放在滚动所有者**内部**,不要在滚动所有者外再包一层带内边距的容器(否则滚动条会漂在内容和面板边界之间)。
- 使用 `Scrollable`、`VirtualList`、`Table`、`DockArea`,而不是用嵌套 `div` 重造。

## 12. 列表、表格与大数据
- 数据可能增长时用虚拟化;行标识与可见位置分离;不要每次渲染克隆整个数据集。
- 有状态的列表/表格负责导航、选择、滚动协调和可见范围计算;条目渲染器只负责行展示。
- 分离:源数据与领域 ID、过滤/排序状态、选择状态、视口/滚动状态、行渲染。
- 宽度、字体、rem 或行内容变化时使条目测量失效;键盘选择和滚动到条目在**模型坐标**中进行。过滤和重排时按领域标识保留选择。

本项目映射:`_search` 命中表格用 DataTable + 虚拟化,行标识用 `_index` + `_id`,不用下标。

## 13. 公共 API 与命名
- 构造函数建立合理默认值;builder 取并返回 `Self`,使用领域语言;回调描述请求的变化,仅在修饰键或指针细节有意义时才带指针事件。
- 行为状态默认私有字段,配 builder 构造和读取方法。公共字段只用于刻意的记录式配置、主题 token、几何和序列化 schema。**每个带公共字段的公共结构体必须加 `#[non_exhaustive]`**,并提供构造函数、`Default` 或 builder。该规则用于新类型和公共 API 变更,无关的既有类型可单独迁移。
- 重组内部结构时保持公共模块路径稳定(模块入口 + 有意的 re-export)。
- 命名模式:
  - 值型渲染控件用名词(`Button`);保留的行为模型 `<Control>State`;命令式共享引用 `<Control>Handle`;语义通知 `<Control>Event`;键盘命令用动词或意图名词(`Confirm`、`Cancel`、`SelectNext`);可插拔数据/行为所有者 `<Role>Delegate` / `<Role>Provider`;应用提供的展示 `render_<part>` 或 `<part>_renderer`;具名区域渲染 `render_<region>`;回调注册 `on_<event>`。
  - 新的流式 builder 不带 `set_`;`&mut self` 修改用 `set_<field>`;非布尔整体替换 builder 用 `with_<field>`。
  - 布尔读取:`is_<形容词>` 或 `has_<名词>`,**不新增 `can_`**(用 `is_closable`,不用 `can_close`)。布尔 builder 可用字段名(`disabled(bool)`),读取用 `is_disabled()`。
  - 零基索引用 `_ix`,不用 `_idx`;已有公共术语如 `selected_index` 保持;ID 后缀 `Id`;一个子系统里不要混用 `idx`/`index`/`ix`。
  - 让外围名称承载语境(`with_item_ix(ix)`,不是 `with_item_ix(item_ix)`);同一类型的字段保持同一缩写层级。
  - 谓词尽量正向命名,但保留 `disabled` 等与控件语义匹配的既有术语。
  - 避免含糊的公共名称:`data`、`item2`、`handle_action`、`update_ui`、`process`、`manager`、`config`。`Manager` 仅在真的协调集合或生命周期时用。
  - 类型擦除包装器仅在真的擦除类型边界时加 `Any` 后缀。
  - 视图和 Entity 按产品概念命名(`ProjectList`);事件处理器按意图命名(`confirm_delete`、`on_query_changed`)。
- 精确词汇:`selected`(持久成员/当前项)、`focused`(键盘目标)、`hovered`(指针存在)、`confirmed`(激活结果)不得混用;`open/close` 用于覆盖层或披露,`show/hide` 用于瞬时展示请求,`expand/collapse` 用于结构;`disabled` 禁止交互,`readonly` 允许导航与选择但禁止编辑(拼写为一个词 `readonly`,标识符、界面文案和文档里都不要写 `read-only`),`loading` 防止重复工作;`index` 是当前位置坐标,`id` 是稳定标识,不要按 index 持久化或索引可重排数据;`placement` 是边/锚点策略,`position` 是已解析几何;`size` 是语义档位,`width/height/bounds` 是几何。
- 回调措辞:`on_click` 只用于真正的点击级契约;Base 里受控的语义原语优先 `on_change(next_value, ...)`。`on_will_change` 可否决/准备,`on_change` 观察,`on_confirm` 提交选择,`on_dismiss` 关闭瞬时界面;文档要写明回调在内部状态变化之前/之后/代替它运行,以及能否同步重入。
- 模块职责单一,状态归属或生命周期无法脱离无关行为理解时就拆文件;组件模块、状态、事件和针对性测试放在一起;使用 `rustfmt` 并满足 Clippy,避免宽泛的 `allow`。
- 注释只记录不变量和意外的生命周期约束,不复述显而易见的 builder 调用。公共文档先说明类型做什么、谁拥有状态;示例用当前可编译的 API 与稳定 ID;写明默认值、平台限制、焦点行为、回调顺序,以及是否需要调用 notify/emit/主题同步。

## 14. 设计总则
- 清晰先于个性;组合先于发明(只有行为真正新才创建新原语);token 先于数值;桌面先于 Web 惯例;状态必须可见;几何解释包含关系;反馈反映真实情况。
- **桌面,不是网页**:默认箭头光标(仅链接用手型);页面导航不是主结构,而是持久窗口/面板/侧栏/标签页/菜单;焦点和滚动显式归属;可调整的桌面外壳并定义最小窗口;关键动作不依赖悬停;默认中等密度。
- 动手前写下:主要任务、被查看/修改的对象、必须随时可用的动作、做决定所需信息、空/加载/错误/离线/只读/无权限状态、键盘路径。不要从仪表盘网格或组件目录开始。
- 对每个提议的动作说出:可见对象、当前状态、范围、结果;做不到就是为时过早。不要仅因后端有能力就暴露它。
- 核心结果的视觉分量要与其重要性匹配,不要缩成小计数或角落图标。

### 层级与强调
- 少量清晰层级:窗口/页面标题 → 区域标题 → 正文 → 弱化文字(次要信息) → 标签。
- 先用字号、字重、间距、分隔线,再加颜色或容器;不要卡片套卡片。
- 强调是有限预算:一个局部表面只有一个清晰焦点;评审时去掉强调色,主任务、当前选择、结果摘要、下一步仍应一目了然。

### 颜色
- 语义角色:`background`/`foreground`;`group_box`、`popover`、`sidebar` 及其前景;`muted`/`muted_foreground`;`primary` 仅用于主要动作或选择强调;`danger`/`warning`/`success`/`info` 只用于其含义;`border`/`input`/焦点环。
- 不要把语义状态色当装饰;**不要只靠颜色传达含义**;每个自定义表面都要在亮/暗主题和自定义主题下验证,不要假设前景是黑、背景是白。

### 圆角、间距、密度
- 圆角用主题的有限档位(`sm`、`md`、`lg`、`xl`…),不要每个元素自创;普通矩形圆角应明显小于短边的一半;`radius_full()` 仅用于有意的圆和胶囊。嵌套表面同心:内圆角 ≈ max(0, 外圆角 − 间距)。圆角要约束整个可见表面,GPUI 中**不要假设圆角父级会裁剪后代**,给内部表面自己的圆角或裁剪,并保留外凸焦点环。
- 间距表达关系(默认刻度约 2/4/8/12/16/24/32 px,对应 xxs…xxl):单控件内部 → 紧密相关控件 → 一个内容组 → 同一区域内的不同组 → 不同区域 → 主要区域边界。组件内边距属于组件,组件之间的间距属于父级;标题与描述的间距小于描述与下一区块的间距;不要重复叠加内边距。这些数值是关系,不是要散落在 feature 代码里的字面量。
- 密度:中等是默认;large 用于引导/稀疏表单,medium 用于大部分界面,small 用于工具栏/菜单/表格,xsmall 仅用于特殊高密度工具,不能作为整个应用的默认。**对整个局部上下文改变密度,而不是单个孤立控件**,并使用组件的 Size API(文字、图标、内边距、命中区一起变),不要只改外框高度。

### 比例与对齐
- 先看内容需求再定比例,避免随意对半分。侧栏给最小/首选/最大宽度,不只给百分比;主从布局保持集合可扫描,详情拿剩余空间(约 1/3 与 2/3 只是起点);检查器和辅助 sheet 默认不遮住主对象,可调整或可关闭;对话框宽度由决策决定;最强的阴影只给最上层决策层,同层内用背景和发丝线表达层级。
- 每个主要区域定义三个尺寸约束:任务仍可用的最小值、舒适默认值、如何消费剩余空间。代表工作流偏好的分栏要持久化,并在恢复时按当前窗口夹取。
- 对齐是结构系统,不是收尾抛光:每个表面确立少量对齐轴(共享的起止边、文字基线、中线、固定功能列);同级元素挂到同一条轴上;兄弟区域共享内容内缩;整个区域重复相同的列几何(表头、行、汇总、加载态、行内编辑);可选内容缺失(图标、徽标、描述、尾部动作)不得移动其余标签,需要时用有意的槽位;嵌套结束时精确回到父轴;缩进只表示真实层级。
- **相等的边缘和间距在渲染像素上必须相等**,一个像素的差异是缺陷,不是可接受的视觉近似。在代表性的窗口尺寸、缩放级别、显示缩放下用测量工具检查已解析的 bounds,不要只凭截图判断。
- 细则:混合字号同行时按**基线**对齐;图标放在固定槽位中居中;可比较的数字右对齐,文字和标识符左对齐;尾部行动作和展开指示放固定宽度列;表单控件按交互框对齐而不是按下方帮助文字;`justify_between` 仅在两侧确实拥有相反边缘时使用;发丝线属于边界所有者,相邻区域不要各画一次;滚动条属于滚动的区域并贴住其尾边。
- 表面与层级:基础窗口表面是平的,用分隔线和背景对比划分区域;弹出层(popover、菜单、对话框、通知)可用逐级更强的阴影;不要给每张卡片加阴影;同类表面共用一种处理(Popover/Select/Combobox/DatePicker/菜单共享同一个主题化的 popover 表面),新增锚定表面时复用它,不要用无关的边框和阴影字面量近似。
- 字体与图标:界面文字用平台 UI 字体,等宽字体只用于代码、标识符、快捷键和需要对齐的数字;避免过多大写和字距,尤其是 CJK;产品内只用一个图标族;图标补充标签而不是替代陌生动作;**仅图标按钮必须有无障碍名称**;填充或彩色图标用来表达状态,不只是装饰。

## 15. 交互规则
- 外壳:单工作区、侧栏工作区、主从、文档工作区(标签页/Dock)、工具窗口。全局导航保持稳定,内容变化。标题栏首先是窗口 chrome:保留拖拽区域,不要把普通标题点击绑定到低频编辑命令;重命名放在显式对象命令后面。
- 窗口缩小时:保住主任务 → 可调整区域到文档记载的最小值 → 折叠次要标签或检查器 → 低频动作进菜单 → 只滚动真正溢出的区域。不得隐藏动作而不提供另一条路径;不要让整个窗口滚动而只有列表或文档主体该滚动。
- 表单与设置:每个字段有可见标签,帮助和校验靠近字段;`Checkbox` 用于独立选项,`RadioGroup` 用于少量可见选项,`Select` 用于较长列表,`Switch` 用于立即生效的设置;提交进行中禁用提交并保留用户输入,结果显示在操作旁;对话框只用于短小聚焦的决定,复杂流程用整页或 sheet;加载态要反映真实等待,已有内容的面板切换应立即完成,骨架屏仅在内容确实在加载且形状已知时使用。
- **命令位置**:主要/高频动作用可见的带标签 Button;当前区域的次要动作放在可见的 `DropdownMenu` 触发器后;作用于指针下对象的命令放 `ContextMenu`(不能是关键命令的唯一入口);重要命令同时提供 Action/键位;悬停才出现的图标只能是快捷方式,命令必须在别处可达;不要为了显得极简把所有动作都塞进菜单。菜单项在任何出现位置都用同一动词、图标、快捷键、启用状态和结果。不要用一排悬停图标按钮,也不要悬停显示唯一的破坏性或关键动作。
- 控件的结果要在点击前可预测:标签说出动作和对象,状态显示可用性,反馈确认同一结果。不要把打开配置流程的按钮叫 `Save`;只从分组移除的按钮不要叫 `Delete`;范围不清时写明范围。对激活立即响应,较长操作时防重复提交,结果显示在发生变化的对象附近;结果本身可见时不加成功消息。
- 每个交互控件的状态:静止、悬停(不能是唯一线索)、按下、弹层打开/按下(持续反馈)、焦点可见(高对比焦点环)、选中/勾选(持久且区别于悬停)、禁用(降低强调、无误导性悬停)、加载(保留上下文、防重复)、错误(说明发生了什么与如何恢复)。选择是信息模型的一部分:标签页、分段选项、可选行、过滤器、导航目的地都必须显示持久的选中态。
- 选中的导航项/列表行/标签用**元素自身的表面**表示(选中填充、更强前景、更粗字重),**不要用前缘竖条或单侧边框**。分段控件是一个轮廓:两端段落跟随容器内圆角,中间段落保持方角,每条分界线粗细一致。
- Button 表示应用操作:primary 仅用于决策区域唯一强调的提交;default 用于普通可见动作;outline 用于需要清晰边界但弱强调;ghost 用于工具栏和行内的低强调动作;icon 仅用于众所周知的符号;`danger` 用于破坏性提交。管理工具栏里的 `Add` 通常用 default Button;表单的默认 `Create` 可用 primary。
- 破坏性操作:区分可逆与不可逆。可逆的优先撤销或临时通知;严重且不可撤销时才用 `AlertDialog`,文案点出具体对象和后果;不要为可逆低风险动作加确认框。
- 覆盖层选最小的:tooltip(短解释/快捷键) → popover → menu → notification(无需决定的异步状态) → dialog(聚焦的决定) → alert dialog(严重确认) → sheet。避免叠放;Esc 关闭最上层,焦点回到触发器或下一个合理目标。Tooltip 只补充缺失的含义,不重复显而易见的动作;Alert 只用于需要立即注意的重要、例外信息。覆盖层里的动作必须指向它实际展示的对象或状态(例如仅当独立的最近历史区可见且有条目时才显示"清除历史");搜索结果、最近项、收藏是不同集合,要分区命名;不适用的动作隐藏,或禁用并说明原因;页脚每一项都要回答对象、为何现在可用、影响范围、执行后哪个可见状态变化。
- 动效用于解释变化,不是装饰:短 transition 用于出现、关闭、展开和空间连续;opacity/transform 能表达时不要动画大面积布局;遵守减少动效偏好;状态理解不依赖动画;不给每个组件加默认动画;独立动画值使用稳定 ID,被打断时从当前采样值平滑反向。动效策略属于样式/应用层,不属于 Base。指针或滚动在相关目标间移动时保持预览表面稳定,只更新内容或位置,交互结束后再关闭,避免反复淡出淡入造成闪烁。
- 数据密集界面:表头和主行标识保持稳定;可比较值对齐,必要时用等宽数字;区分焦点、悬停、活动行、多选;排序与过滤可见且可逆;过滤/重排后按领域 ID 保持选择;虚拟化不改变键盘语义;次要列和检查器渐进披露;空状态解释下一步。一致字段的比较用 table,异质内容扫描用 list,真实层级用 tree,仅当用户需要排布长期工具或文档时才用 dock。不要把复杂数据组件当视觉样式。
- 平台:不要假设各平台能力一致;窗口装饰、无障碍桥接、系统通知、剪贴板、滚动手势、字体、时序都可能不同。平台特定代码放在窄接口后并定义降级行为,保持语义契约。尊重有意义的平台差异(Command/Control、原生窗口装饰、系统外观、滚动条、菜单、通知),信息架构跨平台保持稳定,但不为表面像素一致消除用户熟悉的平台行为。

## 16. 界面文案
- 语境承载语境:侧栏入口只写对象或领域(`Users`,不是 `User Management`;中文写"快捷键",不写"快捷键配置管理");避免 `Management`、`Module`、`Page`、`Function`、`Operation`、`System` 等包装词(除非区分真实领域概念);表格行本身已是操作时可省略泛化的"操作"列名;对话框标题已是问题时正文不再重复提问。这不是为短而删:能改变决策的文字(范围、不可逆后果、异常前提、恢复方式)必须保留。
- 名词表示入口/对象,动词表示命令,形容词或短语表示状态。
- 按各语言的自然表达分别写作,不照搬源语言的语序、词数、客套填充和词性。为重复出现的对象、命令、状态维护一份小型产品词表,工具栏、菜单、右键菜单、对话框、快捷键搜索、文档用同一个词。文案要放回真实界面评审。
- 按钮简短(通常一至两个词),描述结果而非手势或控件:用 `Save`、`Move`、`Delete`(中文"保存""移动""删除"),不用"点击进行保存""确认删除操作"。离开而不提交的统一用 `Cancel`/"取消";`OK` 仅用于确认纯信息。当额外文字能揭示后果或区分易混淆的选择时可更长(如"仅从此分组删除"与"从所有位置删除"、"不保存并重新启动")。确认按钮用最具体的短词:删除对话框用"删除",未保存修改用"放弃修改",纯信息用"知道了"或 OK;`Confirm` 仅在对话框已完整说明复杂承诺且没有准确动词时才作为后备。不要用 `Yes`、`Sure`。
- 确认对话框是一个紧凑的决策:标题写决策或条件(如 `Delete "Roadmap"?`);正文只补充新的范围、后果或恢复信息;操作是取消加具体结果;破坏性样式标记破坏性结果但不能代替准确措辞。避免泛化标题(`Notice`、`Warning`、`Error`、`Confirmation`)和仪式性措辞("您确定要……吗""请注意……""successfully");礼貌来自冷静尊重的语气,不来自重复的"请"。
- 英文用 sentence case(`Reset layout`);专有名词和约定俗成的缩写保持原样。全大写仅用于极短的分组标签、眉题、状态、缩写或代码,**不用于按钮**、长标题、整句或密集列表,同一区域不要同时用全大写、强色和粗体。
- 标签、按钮、菜单项、标签页、标题、占位文字、短状态末尾不加句号;完整的说明、警告、错误句子加完整标点;日常成功或失败消息不用感叹号;中文整句用全角标点,短控件文字同样省略句末标点。
- 用单个省略号字符 `…`,不用三个句点。凡按钮或菜单项会打开对话框、sheet、独立窗口,或命令完成前还需用户输入/选择的,文字末尾加省略(`Settings…`、"导出…");立即执行的命令不加。进行中的任务用不确定进度指示器,不用装饰性的点号。
- 错误说明发生了什么,有帮助时给出下一步恢复方式("无法保存。请检查网络连接后重试。"),不要只显示技术代码或长篇道歉;成功反馈只在结果状态尚不可见时出现(文档已明显进入保存状态就不再弹"保存成功")。
- 国际化:翻译 key 描述稳定意图(`dialog.delete_project.title`),不是源语言句子或屏幕坐标;不要用翻译片段拼句子,不要为恰好英文相同的不同含义复用同一个 key;给每个语言保留语序、复数、标点的控制权;不要按一条英文 label 固定控件宽度;不要把文字放进栅格资源;仅在有 tooltip 等恢复路径时才截断标签。用真实内容、文本膨胀、CJK 排版和应用缩放在组件内验证每个字符串。测试或 lint 应捕获缺失 key、英文资源里的意外 CJK、三点省略号、未经评审的全大写和固定术语不一致,最终仍由人审查。
- 例外:无障碍(A11y)名称和标签可以保持英文,无需本地化;但为操作某个条目的控件命名时,保留条目自身的标签(即使已本地化)。该例外不适用于可见界面文案。
- 技术文档:API 标识符保持原名并用代码格式;链接指向有固定名称的 API/组件/源码/指南时,链接文字用准确的英文名(如 `Font`、`Render`、`Input element`),不翻译也不加多余的 `GPUI Kit` 前缀;周围说明用页面语言;链接只覆盖被引用的名称。

本项目界面语言:中文与英文(见 PRD U5)。中文界面遵循上述全角标点和短标签规则。

## 18. 测试策略
在**能证明行为的最低层**测试:
1. 纯测试:状态转换、几何、解析、排序。
2. GPUI 上下文测试:Entity、事件、订阅。
3. `VisualTestContext` 交互测试:焦点、键盘、指针、布局、渲染状态。
4. 示例或应用冒烟测试:完整工作流。

- 交互组件测试语义契约而非实现细节:指针与键盘激活、受控值变化、禁用行为、焦点移动、事件数量与顺序、稳定标识、重要的空/失败状态。
- 能确定复现的缺陷,**先写回归测试再修复**。
- 依赖真实窗口系统的 UI 行为,通过无障碍树按 role、label、value、启用状态、焦点、选择来测试;每次改变状态后重新读取树(元素下标只是快照);截图只用于语义树表达不了的视觉事实;坐标输入仅作兜底。自动化证据与人工证据分开汇报。
- 不要写"调用内部方法却从不走键盘或指针"的测试。
- 对关键重复的边缘、列、间距加几何断言或视觉回归,并覆盖多个窗口尺寸、rem 缩放和显示缩放。

## 19. 性能
- 不要每帧重建 Entity、订阅、焦点句柄和昂贵数据结构。
- 一次连贯的状态变化后,只通知最窄的所属 Entity。
- 长集合虚拟化,只渲染可见范围。
- 不要为满足闭包而克隆大字符串或集合;捕获稳定句柄或共享数据。
- **先测量再加缓存**,每个缓存必须有明确的失效所有者。
- 动画工作量有界,并遵守减少动效偏好。
- `SharedString` 与 `RenderOnce` 的设计目的是让常见路径廉价,但二者都不承诺零成本;小成本会在大量元素和渲染中累积,对确实的热路径先测量再优化。

## 20. 常见失败模式(避免)
- 一个 Entity 装下整个应用的无关状态
- 业务逻辑和网络请求写进很长的 `render`
- 随机或基于下标的 ElementId 用于可重排内容
- 字面颜色和圆角破坏自定义主题
- 在已有语义组件的地方使用自定义可点击 div
- 本地重复状态与受控模型值漂移
- 每次渲染修改状态导致的 `cx.notify()` 循环
- 嵌套滚动容器没有明确归属
- 为单个界面新增组件变体
- 为可逆低风险动作加确认框
- 测试只调内部方法而不走键盘/指针
- 一行里放满高的列却没写 `items_stretch()`,导致标题被裁

## 21. 设计评审清单(依次回答)
1. **任务清楚吗?** 新用户能否不学习、不猜测、不试错就看懂用途、主要操作和下一步?
2. **操作兑现承诺吗?** 文案、控件、状态、范围、反馈、结果是否描述同一件事?
3. **层级明确而克制吗?** 核心功能是否获得应有空间,同时主按钮、强色、粗体、徽标和警示保持稀缺?
4. **还能做得更少吗?** 能否删除、合并或推迟某个入口、选项、状态而不削弱主任务?
5. **结构准确吗?** 同层内容共享对齐轴,相等间距精确到渲染像素,滚动条贴住实际滚动区域的边缘?
6. **遵守组件体系吗?** 标准控件保留统一几何、状态、键盘与关闭行为,外观来自主题与尺度令牌?
7. **所有状态与约束下都可用吗?** 键盘与焦点、空白、加载、失败、无权限、长翻译、缩放、最小窗口、减少动效。
8. **在真实窗口中验证了吗?** 用真实组件、文案和代表性内容亲手完成任务,而不只看理想截图。
