- 版本:v0.2 草案(v0.1 的产品名 EsDeck 已统一改为 elasticsearch-deck)

## 1. 背景与目标

### 1.1 背景
开发者和运维日常通过 Kibana Dev Tools Console 或 IDE 插件(如 JetBrains Elasticsearch 插件)编写 Elasticsearch REST 请求和 Query DSL。现有方案的不足:
- Kibana Console 必须依赖 Kibana,且无法离线管理多个集群的请求脚本。
- IDE 插件绑定 IDE,体验和能力受宿主限制。
- 浏览器方案对大结果集(几十万行)的展示和滚动性能一般。

### 1.2 产品定位
一款原生桌面应用,专注于 **Elasticsearch REST API 与 Query DSL 的编写、补全、执行和结果浏览**,具备编辑器级别的流畅度,启动快、内存占用低。

### 1.3 目标(可衡量)
| 编号 | 目标 | 指标 |
|---|---|---|
| G1 | DSL 补全准确 | 在基准用例集上,键/值补全的 Top-5 命中率 ≥ 95% |
| G2 | 补全低延迟 | 按键到候选弹出 P95 ≤ 50 ms(本地 schema) |
| G3 | 大结果集流畅 | 10 万行结果表格滚动保持 60 FPS 【待验证】 |
| G4 | 轻量 | 冷启动 ≤ 1.5 s;安装包 ≤ 50 MB 【待验证】 |
| G5 | 版本覆盖 | 支持 Elasticsearch 7.x、8.x(含 9.x 若 schema 可用) |

### 1.4 非目标(v1 不做)
- 不做 Kibana 式的可视化仪表盘、Discover、Lens。
- 不做集群运维管理(分片重分配、快照策略的图形化管理)。
- 不做 OpenSearch 兼容(列入后续评估)。
- 不做云同步与多人协作。
- 不做移动端。

## 2. 目标用户与场景

| 用户 | 典型场景 |
|---|---|
| 后端开发 | 调试搜索 Query DSL,验证 bool/match/range 组合 |
| 搜索/数据工程师 | 反复执行聚合,对比不同参数的结果 |
| SRE/运维 | 查询集群健康、索引状态、_cat 接口,排查问题 |
| 技术支持 | 连接客户集群只读排查,不误改数据 |

核心场景:
1. 连接集群,选索引,写一个 `_search`,边写边补全,执行,查看结果。
2. 保存常用请求,下次直接复用并带变量。
3. 在生产集群上防止误执行危险操作。

## 3. 技术底座与约束

### 3.1 选用 GPUI Kit 的依据
依据官网首页描述,框架已提供以下能力,v1 优先复用而非自研:
- 代码编辑组件:rope 文本结构、Tree-sitter 高亮、LSP 诊断/补全/悬停。
- 虚拟滚动的数据表格(固定列、可调列宽、排序、单元格选择)。
- 可停靠面板(拖拽重排,可序列化)。
- 亮/暗主题与自定义主题(语义 token)。
- AccessKit 无障碍。
- 无头窗口集成测试(模拟指针与键盘,断言状态、焦点、布局与无障碍)。
- 可编译到 wasm32(为后续 Web 版预留)。

开发与设计规范遵循 GPUI Kit 官方 Coding Guides 与 Design Guides,项目内整理为 `.claude/rules/gpui-kit.md`。

### 3.2 技术风险(必须在原型阶段关闭)
| 风险 | 说明 | 处置 |
|---|---|---|
| R1 版本不稳定 | 版本 0.9.x,底层 GPUI API 变动频繁 | 锁定版本与 rev;封装适配层,隔离框架 API |
| R2 中文输入法 | 自绘 UI 的 IME(预编辑、候选窗定位)表现未知 | 原型第 1 周验证;不通过则触发备选方案 |
| R3 官网宣称未核实 | 如 "200K 行稳定"、虚拟表格性能 | 自建基准测试 |
| R4 文档与社区 | 规模未核实 | 预留读源码时间 |
| R5 三平台一致性 | Windows/macOS/Linux 行为差异 | 三平台 CI 构建与冒烟测试 |

### 3.3 备选方案(触发条件:R2 或 R1 原型失败)
Tauri + Monaco + JSON Schema。补全引擎保持独立 crate,可复用。

## 4. 总体架构

```
┌──────────────────────────── App (GPUI Kit) ────────────────────────────┐
│  UI 层: 连接树 | 请求编辑器 | 响应视图 | 历史/收藏 | 设置              │
└───────────────┬───────────────────────────────┬──────────────────────────┘
                │ LSP(进程内/本地通道)           │ 请求执行
        ┌───────▼────────┐               ┌───────▼────────┐
        │ es-dsl-lsp     │               │ es-client      │
        │ 补全/诊断/悬停 │               │ HTTP/认证/TLS  │
        └───────┬────────┘               └───────┬────────┘
        ┌───────▼────────┐               ┌───────▼────────┐
        │ es-dsl-core    │◄──mapping─────┤  Elasticsearch │
        │ 解析+schema索引│               │  集群          │
        └────────────────┘               └────────────────┘
```

模块划分(Cargo workspace):
- `es-dsl-core`:无 UI 依赖。请求行解析、容错 JSON 解析、schema 索引、补全/诊断/悬停算法。
- `es-dsl-lsp`:把 core 包装成 LSP 服务。独立可执行,也能被 VS Code、Zed 使用。
- `es-client`:HTTP 客户端、认证、TLS、超时、取消。
- `es-deck`:GPUI Kit 界面与状态管理。
- `es-deck-schema`:构建脚本,把官方 elasticsearch-specification 的 schema 转为内部索引并随版本打包。

### 5.3 DSL 补全与提示(核心)
| 编号 | 需求 | 优先级 |
|---|---|---|
| A1 | **请求行补全**:HTTP 方法、路径片段、URL 参数,依据 schema 中的 endpoint | P0 |
| A2 | **JSON 键补全**:根据光标处 JSON 路径(如 `query.bool.must[0]`)在 schema 中下钻,列出可用属性 | P0 |
| A3 | **值补全**:枚举、布尔、数值范围提示;对象类型提供结构模板片段(snippet) | P0 |
| A4 | **字段名补全**:`field` 型属性使用目标索引 mapping 中的字段(含 multi-field、嵌套、`.keyword` 子字段),按字段类型过滤(如 `range` 仅提示数值/日期字段) | P0 |
| A5 | **索引名补全**:路径中的索引、别名、数据流(来自 `_cat/indices`、`_alias`) | P0 |
| A6 | **键为用户字段名的结构**(如 `match.<field>`、`term.<field>`、`aggs.<自定义名>`)需单独处理 | P0 |
| A7 | **聚合子结构**:聚合名由用户定义,类型键(`terms`、`date_histogram` 等)由 schema 提供,支持嵌套 `aggs` | P0 |
| A8 | **悬停文档**:显示属性说明、类型、默认值、所属版本 | P1 |
| A9 | **诊断**:未知属性、类型不匹配、必填缺失、已弃用属性、JSON 语法错误,以波浪线标出 | P1 |
| A10 | **版本感知**:候选按当前集群版本过滤;对不可用特性给出提示 | P1 |
| A11 | 补全排序:按使用频率与上下文相关度排序 | P1 |
| A12 | Painless 脚本、ES|QL 的补全 | P2 |
| A13 | 补全对不完整 JSON 保持可用(容错解析) | P0 |

验收用例(示例):
1. 输入 `GET /logs-*/_search\n{ "query": { "` → 候选含 `match`、`term`、`bool`、`range` 等。
2. 在 `"range": { "` 后 → 仅提示 mapping 中的数值/日期字段。
3. 在 `"bool": { "must": [ { "` 内 → 提示完整的查询类型列表。
4. 输入到一半的 JSON(缺右括号)时,补全仍然弹出。
5. 切换连接到 7.x 与 8.x 集群,候选集合随之变化。

### 5.9 多 Tab 与 Data Browser(2026-11-16 新增范围,经产品确认)
- **多 Tab**:每个 Tab 是一个 Console,绑定自己的连接,标题形如 `请求路径 [连接名]`;重启后恢复 Tab 与请求文本(不保存凭据与响应体)。
- **Console 两种类型**:
  - REST Console:现有的请求编辑器 + 响应查看。
  - Data Browser:从左侧树点开索引或别名进入,**只有表格**(不含请求编辑器)。支持分页(`from` / `size`)、点击表头排序、过滤框。
- **过滤框**:输入原样作为 ES `query_string` 发送(例如 `Title:t* AND IMDB_Rating:>7`),不自研语法;语法错误显示服务端返回的原因。
- **只读**:Data Browser 不提供新增行、删除行、编辑单元格;不改变现有写操作的确认与只读模式规则。
- 已知限制:`from + size` 受 `index.max_result_window`(默认 10000)限制,超出时提示,不静默截断。【待验证:翻页超出窗口的处理方式】

## 6. 补全引擎设计要点

### 6.1 数据来源
1. **官方 `elasticsearch-specification`**:提供 endpoint、请求/响应类型的机器可读 schema。构建期转换为内部紧凑索引,按 ES 版本分别打包。
2. **运行期集群数据**:`GET /{index}/_mapping`、`GET _cat/indices`、`GET _alias`,带缓存与手动刷新。

### 6.2 处理流程
1. 文档按请求块切分(请求行 + 请求体)。
2. 请求行:按方法+路径匹配 endpoint,得到参数与请求体类型。
3. 请求体:容错 JSON 解析,保留位置信息,得到光标处的 **JSON 路径**与"键位/值位"状态。
4. 沿 JSON 路径在类型表中下钻,处理联合类型(union)、变体(variants,例如查询类型的键)、字典类型(键由用户定义)。
5. 生成候选,合并 mapping 动态数据,按类型过滤并排序。

### 6.3 已知难点
- schema 中的类型包含联合、泛型、容器变体和"简写形式"(如 `"term": {"field": "value"}` 与 `{"field": {"value": ...}}`)。
- 部分 API 不遵循标准 JSON 请求体(NDJSON)。
- schema 与实际集群版本可能存在差异;字段 mapping 可能很大(数万字段),需要增量加载与索引。

### 6.4 测试策略
- 基准用例集:从官方文档和 Kibana 示例整理,按期望候选编写表驱动测试。
- GPUI Kit 无头集成测试:模拟键盘输入并断言补全弹层。
- 属性测试:对任意 JSON 前缀,补全引擎不得 panic。
